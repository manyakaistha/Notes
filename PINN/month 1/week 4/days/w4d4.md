## 1. Day 4 Overview & Daily Goals

In standard machine learning, Adam with mini-batches is typically run until convergence. In scientific PINN training, however, Adam frequently stalls at loss values around $10^{-2}$ or $10^{-3}$, unable to resolve fine physical features. To achieve the high precision demanded by engineering ($\sim 10^{-6}$), practitioners employ the **Two-Phase Optimization Protocol**.

The primary goals of Day 4 are:
1. Understand why first-order gradient descent stalls in stiff, narrow PDE loss valleys.
2. Master the mathematical mechanics of the quasi-Newton L-BFGS algorithm.
3. Implement PyTorch's required `closure()` function pattern for second-order line searches.
4. Execute the two-phase workflow (Adam $\to$ L-BFGS) and observe superlinear loss collapse.

## 2. Prerequisite Diagnostic Checkpoint

### Diagnostic Questions & Authoritative Solutions

#### 1. Why does PyTorch require a `closure()` callable for `optimizer.step()` in L-BFGS?
- L-BFGS performs line searches (such as the Strong Wolfe conditions) to determine the optimal step length $\alpha_k$ along the quasi-Newton search direction $\mathbf{p}_k = -\mathbf{H}_k^{-1} \mathbf{g}_k$. A line search requires re-evaluating the objective function and its gradient multiple times at test points along $\mathbf{p}_k$. Passing a `closure()` function enables the optimizer to repeatedly re-compute the forward and backward passes internally.

#### 2. Why should we NOT train with L-BFGS directly from random initialization?
- At random initialization, the parameter state is far from the true physical basin. L-BFGS's quadratic model of the loss surface is inaccurate in highly non-convex, rugged regions, often leading to line-search failures, premature termination, or convergence to unphysical local minima. Adam is far more robust for initial global exploration.

#### 3. Why is L-BFGS used with full-batch training rather than mini-batching?
- L-BFGS constructs its approximation of the inverse Hessian from differences between successive gradient vectors: $\mathbf{s}_k = \theta_{k+1} - \theta_k$ and $\mathbf{y}_k = \mathbf{g}_{k+1} - \mathbf{g}_k$. If mini-batching is used, the gradient fluctuates randomly from batch to batch, corrupting $\mathbf{y}_k$ with stochastic noise and invalidating the curvature estimate.

## 3. Core Theory: The Two-Phase Optimization Protocol

```
Phase 1: Global Basin Exploration (Adam)
• Random Initialization ──> Robust gradient updates
• Coarse resolution of boundary conditions and bulk dynamics
• Stalls at loss ~ 10^-2 to 10^-3
                 │
                 ▼
Phase 2: Superlinear Fine-Tuning (L-BFGS)
• Full-batch deterministic mode with Strong Wolfe line search
• Curvature-aware inverse Hessian approximation
• Drives residual down to machine precision ~ 10^-6
```

## 4. Practical Laboratory: Executing the Two-Phase Protocol

### 4.1 Concept → Code → Output → Interpretation

#### 1. Concept
We train the damped oscillator PINN ($m=1.0, \mu=2.0, k=20.0$) using 100 iterations of Adam (Phase 1), followed immediately by 20 iterations of full-batch L-BFGS (Phase 2), observing the sudden order-of-magnitude reduction in loss and error.

#### 2. Code
```python
import torch
import torch.nn as nn
import numpy as np

torch.manual_seed(42)

# Model architecture
pinn = nn.Sequential(
    nn.Linear(1, 32),
    nn.Tanh(),
    nn.Linear(32, 32),
    nn.Tanh(),
    nn.Linear(32, 1)
)

t_c = torch.linspace(0.0, 1.0, 40, requires_grad=True).unsqueeze(1)
t_0 = torch.tensor([[0.0]], requires_grad=True)

def compute_loss():
    # Interior ODE
    u_c = pinn(t_c)
    u_t = torch.autograd.grad(u_c, t_c, torch.ones_like(u_c), create_graph=True)[0]
    u_tt = torch.autograd.grad(u_t, t_c, torch.ones_like(u_t), create_graph=True)[0]
    res = u_tt + 2.0 * u_t + 20.0 * u_c
    l_ode = torch.mean(res**2)

    # Initial Condition
    u_0 = pinn(t_0)
    u_0_t = torch.autograd.grad(u_0, t_0, torch.ones_like(u_0), create_graph=True)[0]
    l_ic = (u_0 - 1.0)**2 + (u_0_t - 0.0)**2

    return l_ode + 20.0 * l_ic

# Phase 1: Adam Pre-training
opt_adam = torch.optim.Adam(pinn.parameters(), lr=0.01)
print("--- Phase 1: Adam Optimization ---")
for epoch in range(1, 101):
    opt_adam.zero_grad()
    loss = compute_loss()
    loss.backward()
    opt_adam.step()
    if epoch in [1, 50, 100]:
        print(f"Adam Iteration {epoch:03d} | Total Loss: {loss.item():.5f}")

# Phase 2: L-BFGS Fine-Tuning
opt_lbfgs = torch.optim.LBFGS(
    pinn.parameters(),
    lr=1.0,
    max_iter=20,
    history_size=50,
    line_search_fn="strong_wolfe"
)

print("\n--- Phase 2: L-BFGS Quasi-Newton Fine-Tuning ---")
step_count = [0]
def closure():
    opt_lbfgs.zero_grad()
    l = compute_loss()
    l.backward()
    step_count[0] += 1
    if step_count[0] in [1, 5, 10, 20]:
        print(f"L-BFGS Eval {step_count[0]:02d}     | Total Loss: {l.item():.7f}")
    return l

opt_lbfgs.step(closure)

# Final Error Evaluation
with torch.no_grad():
    t_eval = t_c.detach()
    u_pred = pinn(t_eval).numpy().flatten()
    t_np = t_eval.numpy().flatten()
    u_true = np.exp(-1.0 * t_np) * (np.cos(np.sqrt(19.0) * t_np) + (1.0 / np.sqrt(19.0)) * np.sin(np.sqrt(19.0) * t_np))
    final_l2 = np.linalg.norm(u_pred - u_true) / np.linalg.norm(u_true)

print("-" * 50)
print(f"Final Relative L2 Error: {final_l2:.5e}")
```

#### 3. Output
```text
--- Phase 1: Adam Optimization ---
Adam Iteration 001 | Total Loss: 43.17763
Adam Iteration 050 | Total Loss: 16.77194
Adam Iteration 100 | Total Loss: 15.35398

--- Phase 2: L-BFGS Quasi-Newton Fine-Tuning ---
L-BFGS Eval 01     | Total Loss: 15.3400213
L-BFGS Eval 05     | Total Loss: 0.1284511
L-BFGS Eval 10     | Total Loss: 0.0034190
L-BFGS Eval 20     | Total Loss: 0.0001048
--------------------------------------------------
Final Relative L2 Error: 1.48201e-03
```

#### 4. Interpretation
In Phase 1, Adam brings the loss down from $43.177$ to $15.353$ over 100 iterations. Switching to L-BFGS in Phase 2 causes a dramatic acceleration: within just 20 function evaluations, L-BFGS drives the loss down from $15.34$ to **$0.0001048$**—a reduction of over **$140,000\times$**! The relative $L_2$ error reaches $1.48 \times 10^{-3}$, illustrating the power of the two-phase optimization standard.

## 5. Daily Knowledge Mastery Checkpoint

### Problem 1: L-BFGS Memory Footprint
**Question:** In `torch.optim.LBFGS(..., history_size=50)`, what does `history_size=50` mean mathematically, and how does memory usage scale?  
**Authoritative Solution:**  
L-BFGS does not store the full $P \times P$ Hessian matrix (which would require gigabytes for large networks). Instead, it stores the $m=50$ most recent parameter difference vectors $\mathbf{s}_k = \theta_{k+1} - \theta_k$ and gradient difference vectors $\mathbf{y}_k = \mathbf{g}_{k+1} - \mathbf{g}_k$. Memory usage scales strictly as $\mathcal{O}(2 \cdot m \cdot P)$, which is linear with respect to the parameter count $P$.

### Problem 2: Line Search Failure Diagnostics
**Question:** What does it indicate if L-BFGS stops after 2 iterations with the message "Line search failed to satisfy Wolfe conditions"?  
**Authoritative Solution:**  
It indicates that the loss surface is too steep, noisy, or ill-conditioned along the proposed quasi-Newton direction for the step size to produce sufficient decrease. Common causes include: (1) switching to L-BFGS too early before Adam has smoothed the loss; (2) using stochastic mini-batches instead of full batches; or (3) gradient explosion caused by unnormalized coordinate inputs.
